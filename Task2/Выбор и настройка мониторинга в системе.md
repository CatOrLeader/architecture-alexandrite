# Выбор и настройка мониторинга в системе

## Мотивация

Яндекс Метрика показывает работу сайта, но не прохождение B2B-заказов через MES, RabbitMQ и CRM. Мониторинг поможет обнаруживать задержки до жалобы, находить перегруженный компонент и проверять исправления. Данные о просроченных заказах и запасе производительности позволят обосновать расходы на инфраструктуру. Причины задержек пока неизвестны: потерю сообщений, медленные запросы к БД и конкуренцию за CPU нужно проверить измерениями.

## Выбор подхода к мониторингу

| Часть системы | Подход | Что отслеживаем |
|---|---|---|
| Shop API, CRM API, MES API | RED | Частоту запросов, ошибки и длительность по операциям |
| VM приложений, PostgreSQL и RabbitMQ | USE | Использование ресурсов, ожидание свободного ресурса и ошибки |
| Очереди и обработчики RabbitMQ | RED + USE | Скорость обработки, ошибки, накопление сообщений и время ожидания |

Расчёт стоимости учитываем отдельно от HTTP-запроса: он занимает в среднем 2–3 минуты, а для сложной модели до 30 минут. Добавляем бизнес-метрики прохождения заказов.

## Метрики и ярлыки

Мониторинг охватывает три API, общую Shop DB магазина и CRM, отдельную MES DB, RabbitMQ и S3. Общие ярлыки: `env` и `service`; для ресурсов — `instance`. `route` — шаблон `/orders/{id}`, `channel` — `b2c`, `b2b` или `internal`. Остальные значения ярлыков ограничены справочниками.

| Метрика | Зачем нужна | Дополнительные ярлыки |
|---|---|---|
| Количество HTTP-запросов и RPS всех API | Видеть нагрузку и долю ошибок; HTTP 200 и 500 получаем из одного счётчика | `route`, `method`, `status_code`, `channel` |
| Длительность HTTP-запросов, p50/p95/p99 | Находить медленные операции, особенно список MES | `route`, `method`, `outcome` |
| CPU и очередь выполнения на VM API | Проверять, мешает ли расчёт MES обслуживанию запросов | `role` |
| Память, swap и OOM у API, обеих БД и RabbitMQ | Обнаруживать нехватку памяти и перезапуски | `role` |
| Подключения PostgreSQL и ожидание соединения в пулах API | Выявлять исчерпание подключений | `db`, `pool`, `state` |
| Длительность SQL и блокировки PostgreSQL | Проверять причины медленного дашборда и конкуренцию магазина с CRM | `db`, `operation` из списка запросов |
| Размер обеих БД и свободное место | Планировать расширение и предотвращать остановку записи | `db` |
| Размер S3-хранилища и число объектов | Контролировать рост моделей и расходы на хранение | `bucket_role` |
| Полученные и отправленные байты API | Оценивать нагрузку от моделей и размер ответов списка | `route`, `direction` |
| RabbitMQ ready и unacked | Различать ожидающие доставки сообщения и доставленные, но неподтверждённые | `vhost`, `queue` |
| Скорость публикации, подтверждений, повторной доставки и ошибки публикации | Находить отставание обработчиков и сбои передачи | `queue`, `outcome` |
| Глубина DLQ и число переводов в неё | Обнаруживать сообщения, которые не удалось обработать | `queue`, `reason` |
| Время ожидания и выполнения расчёта, ошибки | Отличать нехватку workers от длительного вычисления | `channel`, `complexity_bucket`, `outcome` |
| Количество заказов по статусам, возраст этапа и число просроченных | Видеть зависшие заказы и риск нарушения обещанного срока | `channel`, `status` |
| Доступность экспортёров и время последнего обновления | Отличать отсутствие ошибок от неисправности мониторинга | `target` |

DLX маршрутизирует отклонённые сообщения, но не хранит их: измеряем привязанные DLQ. In flight соответствует `unacked`. Источник бизнес-метрик — подтверждённые переходы и текущее состояние заказов в PostgreSQL.

Идентификаторы пользователей и заказов не добавляем в ярлыки: они создают неограниченное число рядов. RPS конкретного клиента разбираем по логам.

## План действий

1. Развернуть Prometheus, Grafana и Alertmanager для хранения метрик, дашбордов и уведомлений.
2. Подключить Micrometer/Actuator в Java, .NET metrics в MES, Node Exporter на VM и штатный Prometheus-плагин RabbitMQ. Получать метрики PostgreSQL и S3 через доступные средства managed-сервисов.
3. Добавить измерения расчёта и агрегаты заказов из PostgreSQL. Согласовать ярлыки; отделить dev, release и prod.
4. Собрать дашборды технического состояния и прохождения B2C/B2B-заказов. Закрыть служебные endpoints во внутренней сети, предоставить сотрудникам доступ по ролям.
5. За две недели собрать исходные значения, затем согласовать правила уведомлений и ответственных. На release проверить остановку API, consumer и экспортёра, а также появление сообщения в DLQ.
